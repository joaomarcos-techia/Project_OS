# ADR-007 — RLS implementation patterns (FORCE-principal + dual-context + single helper)

**Status:** accepted
**Date:** 2026-05-27

## Context

ADR-002 decided to USE Postgres RLS as the multi-tenant isolation defense. ADR-007 fixes HOW to implement that decision in C2+.

The Supabase Transaction Pooler exposes the database via the role `postgres.<projectref>`, which holds `BYPASSRLS`. Without `FORCE ROW LEVEL SECURITY`, the table owner — and the pool role acting as owner — bypasses every policy. RLS becomes theater.

Two complementary issues compound that risk: (1) policies that read only `auth.jwt() ->> 'clinic_id'` work for HTTP requests but silently break jobs/workers (no JWT); policies that read only `current_setting('app.current_clinic')` work for jobs but silently break HTTP. (2) Without a single SQL helper for claim names, the predicate `coalesce(auth.jwt() ->> 'role', '')` will appear in 30+ tables by C16 — every copy is a typo waiting to happen.

C2 is the camada where these patterns become invariant for everything that follows.

## Decision

**Hierarchy (D24):** FORCE ROW LEVEL SECURITY is the **principal** defense. `SET LOCAL ROLE authenticated` (inside `withTenant`) is **hardening only**. The invariant chosen is the Postgres one — stable across pooler/grant/Supabase changes. If the hardening ever fails, isolation continues; defense in depth degrades.

**10 invariants frozen in C2:**

1. `ENABLE` + `FORCE` ROW LEVEL SECURITY in the SAME migration as `CREATE TABLE`. The sole documented exception is `_schema_version` (operational metadata, see invariant #10).
2. Every default tenant policy is generated by `defaultTenantPolicy()` from [src/lib/db/rls.ts](../../src/lib/db/rls.ts). Custom policies require a comment justifying the deviation and, when the deviation introduces a new pattern, a follow-up ADR.
3. `withTenant(clinicId, fn)` ([src/lib/db/tenant.ts](../../src/lib/db/tenant.ts)) runs `SET LOCAL ROLE authenticated` BEFORE `set_config('app.current_clinic', ...)`. This is hardening, not isolation. The pre-implementation gate that validated this is `SET LOCAL ROLE authenticated; SELECT current_role` returning `authenticated` on `qoro-dev` Transaction Pooler.
4. **Dual-context (D22):** every policy predicate compares against `current_setting('app.current_clinic')` OR `current_clinic_id()`. Never one or the other alone. Jobs/workers/scripts rely on the GUC; HTTP requests rely on the JWT. Same rule applies to `clinics`, where the column compared is `id` (the tenant itself).
5. Pool reuse is safe because `SET LOCAL` (role and GUC) is scoped to the active transaction. Validated by `BEGIN; SET LOCAL ROLE authenticated; SELECT current_role; COMMIT; SELECT current_role` returning `authenticated` then the pool role.
6. Default policies do NOT use `TO authenticated`. Without role binding, FORCE RLS still applies under any non-bypass role. The sole exception is `_reserved_slugs.reserved_slugs_read`, which is a semantic SELECT for authenticated users (slug validation at signup).
7. Policies must operate when `auth.jwt()` returns NULL. The SQL helpers `current_clinic_id()` and `current_platform_role()` wrap the JWT lookup in `coalesce(..., '')`. Removing that wrapper silently breaks every job/script context.
8. Hard delete of `clinics` is permitted only through explicit super_admin flows (D26). The cascade is total. C15 may NOT expose a delete endpoint without dual confirmation, audit trail (C4), and a 30-day soft-delete window (C13). In C2–C14, deletion happens only via psql or Drizzle Studio.
9. **RLS ≠ RBAC (D27).** Policies answer "may the caller touch this tenant?" — never "which role may edit?". Functional authorization (gestor may edit clinic name; doctor may not) lives in the application layer (Server Actions call `requireRole(...)` before the query). The single carve-out in the database is `super_admin`, which is the cross-tenant exception that does not fit RBAC. Mixing role predicates into RLS silently breaks jobs/workers without JWT and explodes the policy combinatorial in months.
10. **Three table categories (D29).** Every new table picks exactly one:
    - **Tenant-scoped** (has `clinic_id` FK): `ENABLE + FORCE RLS` + `defaultTenantPolicy()`. Index on `clinic_id` (Postgres does not create one for FKs).
    - **Global protected** (no `clinic_id`, but not world-readable — e.g., `feature_flags`, `ai_prompts`, `billing_catalog`): `ENABLE + FORCE RLS` + super_admin-only OR semantic policy like `_reserved_slugs`.
    - **Operational metadata** (no sensitive data, e.g., `_schema_version`): admin-only access. The acceptable end-state is EITHER `rls=f, force=f, no policies` (strict D20) OR `rls=t, force=f, no policies` (Supabase auto-enabled — admin-only via BYPASSRLS roles `postgres`, `service_role`). Both are equivalent: no non-bypass role can read. `_schema_version` in `qoro-dev` is in the second state; documented as accepted in audit round 5. Requires a written justification in the PR. The default for any new table is category 1 or 2.

11. **Custom functions are NEVER granted to PUBLIC (D36).** `CREATE FUNCTION` defaults to `GRANT EXECUTE ... TO PUBLIC`. Any new role added in C3+ would silently inherit EXECUTE. Pattern enforced by C2 hardening migration 0002:
    - `REVOKE EXECUTE ... FROM PUBLIC` immediately after `CREATE FUNCTION`.
    - `GRANT EXECUTE ... TO anon, authenticated, service_role` only — never PUBLIC.
    - `anon` retains EXECUTE on RLS helper functions intentionally: without EXECUTE, anon queries throw `permission denied for function` instead of returning 0 rows, which is information disclosure. Returning 0 rows leaks strictly less than confirming function existence.
    - `postgres` role retains EXECUTE by ownership (function creator).
    - Every new function in C3+ migrations MUST follow the same REVOKE/GRANT pattern in the same migration as `CREATE FUNCTION`.

**Supporting decisions:**

- **`defaultTenantPolicy()` is baseline, not destination (D32).** When multi-tenant-shared scenarios appear (marketplace, partner clinics, shared auditor) custom policies are accepted with a new ADR.
- **`defaultTenantPolicy()` emits a fingerprint (D28).** Every generated block opens with `-- GENERATED_BY: defaultTenantPolicy(v1)`. Audit tooling distinguishes helper output from manual policies via grep. The version bumps when the template changes.
- **Identifier sanitation (D23 + D30).** The helper applies `.trim().toLowerCase()` to every interpolated identifier and validates against `/^[a-z_][a-z0-9_]*$/`. Today only devs call the helper; this guard eliminates the footgun where a future caller derives the table name from config/env.
- **SQL helpers for JWT claims (D33).** `current_clinic_id()`, `current_platform_role()`, `is_super_admin()` are installed by migration 0001. Policies invoke these helpers instead of repeating `coalesce(auth.jwt() ->> '...', '')`. Single source of claim names; the planner inlines `STABLE` functions.

**Operational pre-condition:** If `SET LOCAL ROLE authenticated` ever stops being permitted for the pool role, hardening degrades but isolation continues (FORCE + dual-context still apply). The system is not re-architected; only re-evaluated operationally.

## Threat Model

**Trust boundaries (C2):**

| Boundary | Threats accepted | Threats rejected |
|---|---|---|
| External HTTP (Supabase Auth + PostgREST) | None — PostgREST validates JWT signature server-side before injecting `request.jwt.claims` | Forged JWTs, expired tokens, tampered claims |
| Internal server code (Server Actions, Workers, Scripts) | Code is trusted; bugs are mitigated by patterns + lint + RLS as defense-in-depth | N/A (trust boundary INTERIOR to system) |
| Direct DB access via `postgres-js` (Drizzle pools) | Server-side only; cannot be exposed to external HTTP | N/A |
| `super_admin` claim | Trusted to come from Auth Hook (C3) only | Self-issued claims in app code (see PROIBIDO below) |

**ABSOLUTAMENTE PROIBIDO em código de aplicação:**

1. **`SELECT set_config('request.jwt.claims', '{...}', ...)`** — esse GUC pertence ao PostgREST/Supabase Auth. Setá-lo em código backend equivale a forjar JWT claims em texto plano (verificado empiricamente: setar `{"role":"super_admin"}` dentro de transação com role `authenticated` bypassa todo isolamento). Workers/scripts NUNCA precisam disso — usam `withTenant()` que controla apenas `app.current_clinic`.

2. **`db.<query>()` direto fora de `withTenant()`** em código tenant-scoped. O pool roda como `postgres.<projectref>` (BYPASSRLS) — queries diretas leem cross-tenant. C3+ terá lint rule barrando isso. Em C2, regra cultural.

3. **`dbAdmin.<query>()`** fora dos paths allowlisted (`src/app/(admin)/`, `src/app/api/admin/`, `scripts/`). ESLint enforça.

4. **`SET ROLE postgres`** ou qualquer role com BYPASSRLS dentro de Server Actions / handlers tenant-scoped. Quebra RLS para a sessão inteira até COMMIT.

5. **Tabelas tenant-scoped sem `FORCE ROW LEVEL SECURITY`** — sem FORCE, owner bypassa policies.

6. **Policies sem `defaultTenantPolicy()`** sem justificativa SQL + ADR.

7. **`CREATE FUNCTION` sem REVOKE/GRANT explícito** (invariante #11) — herda PUBLIC EXECUTE.

8. **`auth.jwt() ->> 'X'` literal em policy** em vez de helper `current_X()` — drift de claim name garantido em 6 meses.

**GARANTIAS estruturais (válidas em produção):**

1. JWT claims em runtime HTTP vêm SOMENTE de PostgREST após validação de assinatura.
2. `withTenant(clinicId, fn)` é o único setter aprovado de `app.current_clinic`. Não toca `request.jwt.claims`.
3. `app.current_clinic` é confiável APENAS dentro da transação em que foi setado. SAVEPOINT rollback restaura valor anterior (verificado empiricamente).
4. FORCE RLS garante isolamento mesmo se SET LOCAL ROLE quebrar em ambientes futuros.
5. `pg_policy` é a única fonte da verdade de regras de acesso — código de aplicação NUNCA reimplementa lógica de isolamento.

**Exemplo CORRETO (worker/script):**
```ts
// requireClinicId() vem de C3 — em C2, o worker recebe clinicId como input validado
const clinicId = job.payload.clinicId;
await withTenant(clinicId, async (tx) => {
  // todas as queries via tx respeitam RLS automaticamente
  await tx.select().from(clinicUnits);
});
```

**Exemplo INCORRETO (anti-pattern):**
```ts
// ❌ Forja claim
await db.execute(sql`SELECT set_config('request.jwt.claims','{"role":"super_admin"}',true)`);
// ❌ Direct query sem withTenant
const all = await db.select().from(clinicUnits); // cross-tenant via pool role
// ❌ dbAdmin em código tenant-scoped
import { dbAdmin } from '@/lib/db'; // ESLint barra
```

## Consequences

- RLS is testable from C2 alone (no login flow needed yet) via psql with `SET ROLE` and `set_config('request.jwt.claims', ...)`. The validation suite for these patterns lives in [docs/runbooks/c2-validation.md](../runbooks/c2-validation.md).
- Forgetting `FORCE` on a future tenant-scoped table is a silent leak. The anti-leak checklist (`docs/CONVENTIONS.md`, new-table template) blocks this in PR review.
- Forgetting either branch (GUC or JWT) breaks half the system. The dual-context invariant + SQL helpers make the predicate hard to misremember.
- Future migration to a second Supabase project, a self-hosted Postgres, or PostgREST as a separate access path is straightforward — the patterns above do not depend on Supabase-specific machinery beyond `auth.jwt()`.
- Custom policies for marketplace / shared-tenant scenarios remain possible without throwing away the baseline.

## Alternatives

- **`ENABLE` without `FORCE`:** rejected — the owner of the table bypasses every policy.
- **`SET LOCAL ROLE authenticated` as the only defense:** rejected — depends on pool/role privileges that may change; isolation must not be a single hop away from theater.
- **Policies that read only JWT:** rejected — jobs/workers/scripts have no JWT and lose access silently.
- **Policies that read only GUC:** rejected — HTTP request handlers in C3 will not set the GUC by default; sessions rely on JWT.
- **`TO authenticated` on default policies:** rejected — couples isolation to the role-switching mechanism (D24 inverts that hierarchy).
- **One policy per role (`gestor`, `owner`, etc.):** rejected — that is RBAC, not isolation. Combinatorial explodes; jobs without JWT lose access (D27).
- **A second Supabase project to separate `db` from `dbAdmin` in C2:** rejected — operational cost (two projects, DNS, credentials) without isolation gain; FORCE + dual-context already make `db` safe.
- **Skip the SQL helper functions:** rejected — `coalesce(auth.jwt() ->> '...', '')` repeated 30 times by C16 produces drift; a single STABLE function is identical to the planner.
- **Keep PUBLIC EXECUTE on SQL helpers** (default Postgres behavior): rejected — any new role added in C3+ would silently inherit EXECUTE on helpers, violating least-privilege. Explicit REVOKE + GRANT is the production-grade default. See invariant #11 + migration 0002.
- **Revoke EXECUTE from anon on RLS helpers (full lockdown):** rejected — anon queries fire policies that call helpers; without EXECUTE, queries throw `permission denied for function` instead of returning 0 rows. The error is information disclosure (confirms function exists). Returning 0 rows leaks strictly less.
